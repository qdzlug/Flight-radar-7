# AGENTS.md

Working notes for agents and contributors on this repository.

## What this project is

An ESP32-S3 (Elecrow CrowPanel Advance 7" HMI) flight radar. The firmware
downloads nearby aircraft state vectors, draws them on an animated radar, and
shows a detail card for the selected aircraft. The UI is generated by
SquareLine Studio, so treat `src/main/ui/` as mostly generated code.

Two halves:

- `src/` — ESP-IDF firmware (C, LVGL 8, FreeRTOS).
- `server/` — optional FastAPI merge service that proxies and enriches the
  aircraft data (Python).

## Current work: data source indirection + merge service

The goal is to let the radar point at an arbitrary data source instead of
talking to OpenSky directly, with a merge service that fills in the fields
OpenSky's public API does not publish.

### Firmware

- `opensky_client.c` reads a data source URL from NVS (`radar` / `dataurl`) and
  requests it first, appending `lamin`/`lamax`/`lomin`/`lomax`. If that request
  fails, or no URL is configured, it falls back to OpenSky with OAuth2.
  `FetchStates()` is the shared HTTP path; the auth header and TLS setup are
  applied only for the OpenSky path, so a plain `http://` LAN URL works.
- `webserver.c` serves a small config page: a `credentials.json` upload for
  OpenSky and a text field for the data source URL. `POST /setdata` validates
  the URL and calls `OpenSky_SetDataUrl()`. An empty field clears it.
- `opensky_client.c` parses state vector indices 17/18/19 (`category`,
  `typecode`, `registration`) and shows the typecode next to the callsign in
  the Name card (`UpdateSelectedAircraftUI` in `main.c`).
- The radar settings dialog gained Range and Poll fields, saved as NVS blobs
  under `radar` (`lat`, `lon`, `range`, `poll`). Poll is clamped to 10-120 s and
  range to 5-200 km. `LoadRadarSettings` defaults poll to 25 s when the key is
  absent, so devices upgraded from an older firmware keep working.

### Server (`server/`)

`app/main.py` exposes `GET /states/all` (plus `/states` and `/`), takes the four
OpenSky bounding-box parameters, and returns a merged response. `app/sources.py`
fetches OpenSky, adsb.lol, adsb.fi, adsb.im (needs `ADSB_IM_URL`, skipped when
empty) and an optional local tar1090 concurrently, each under an overall
deadline (`_collect` in `app/main.py`). `app/merge.py` combines them; the first
source that answered is the base, so a failed OpenSky is not mislabelled in
`meta`. `app/enrichment.py` optionally adds route/flight status from FlightAware
(`ENRICHMENT_PROVIDER`, fail-open, cached in SQLite, rate limited). `app/statevector.py` normalises every source into
the same 20-field row.

- The data-source request uses an 8 s timeout (OpenSky keeps 15 s). After a
  failure with OpenSky credentials configured, the data source is skipped for
  60 s and the poll goes straight to OpenSky; `OpenSky_SetDataUrl()` clears the
  backoff. Without credentials there is no fallback, so it keeps retrying. This
  change has not been built or run on the device.

## Details worth knowing

**OpenSky's documented REST response has 17 fields, not 20.** An anonymous
`/api/states/all` request returns rows of length 17: no `category` (17),
`typecode` (18) or `registration` (19). That is why the aircraft type feature
needed a second data source. Do not assume indices 17-19 are populated when
talking to OpenSky directly.

**ADS-B sources use imperial units.** The readb/tar1090 family (adsb.lol,
adsb.fi, dump1090) reports altitude in feet, ground speed in knots, and vertical
rate in feet per minute. OpenSky reports metres and m/s. The firmware multiplies
by `3.28084` and `3.6` for display, so the merge service converts on the way in
(`FT_TO_M`, `KT_TO_MPS`, `FPM_TO_MPS` in `app/statevector.py`). Skipping this
conversion makes the display wrong by a factor of ~3.3 with no obvious error.

**ADS-B emitter categories are offset by one from OpenSky's integers.** `A5` is
a heavy aircraft, which OpenSky calls `6`, not `5` (high vortex large). The full
table is `EMITTER_CATEGORY` in `app/statevector.py`, including the surface
vehicle and glider/UAV sets. The firmware's `GetCategoryName()` expects
OpenSky's numbering, so this mapping has to be right or every category label is
wrong.

**The ESP32 fetches into a 64 KiB buffer** (`responseCapacity` in
`opensky_client.c`) and fails the entire request if the response overflows it.
A fully enriched row is about 220 bytes, so `MAX_STATES=150` lands near 33 KiB.
Raising it much past ~250 risks the device silently discarding every response.

**Non-ICAO addresses must be dropped.** readb sources prefix addresses derived
from TIS-B or MLAT with `~`. Those are not real ICAO24 addresses, so they are
filtered out by `normalise_icao24()`.

**ADS-B sources are queried by radius, not by box.** The service converts the
bounding box to a centre point plus a radius in nautical miles, capped at 250 nm
by the upstream APIs, then filters results back to the exact box. Filtering to
the box is safe because the radar draws inside the inscribed circle.

## Fixed bug: data source was never used on a fresh device

`OpenSky_HasDataSource()` only returned true after `LoadDataUrl()` had run, and
`LoadDataUrl()` was called from inside `OpenSky_GetAircraftJson()`. The poll task
in `main.c` is gated on `OpenSky_HasCredentials() || OpenSky_HasDataSource()`,
so a device configured with only a data source and no OpenSky credentials never
reached the fetch at all, and never populated the value it was gated on. The URL
is now loaded on demand by `OpenSky_HasDataSource()` and in `OpenSky_Init()`,
guarded by a mutex, and updated in place by `OpenSky_SetDataUrl()`. The web page
no longer writes NVS directly.

## Build and flash

Requires ESP-IDF 5.5.x. Note that IDF's Python environment is built for the
system Python, so a venv active in the shell will break `export.sh`:

```bash
PATH="/usr/bin:/usr/sbin:/bin:/usr/local/bin:$PATH" \
  bash -c 'unset VIRTUAL_ENV; source ~/esp/esp-idf/export.sh; cd src && idf.py build'
```

Flash and monitor use `/dev/cu.wchusbserial10` on this machine. The project
targets `esp32s3`. `src/build/` and `.venv/` are ignored and must not be
committed.

A pre-existing, unrelated warning: `bm8563_min.h` redefines `I2C_MASTER_NUM`,
which `waveshare_rgb_lcd_port.h` already defines. It is harmless.

## Tests

```bash
python -m pytest server/tests -q
```

57 tests, no network access. They cover unit conversion, the emitter category
map, merge precedence and conflict resolution, and the API's cache, stale
serving and upstream-failure paths. The firmware has no test harness.

Smoke test the merge service against live upstreams:

```bash
cd server && python -m uvicorn app.main:app --port 8000
curl "http://localhost:8000/states/all?lamin=13.10&lamax=13.30&lomin=77.60&lomax=77.80"
```

`X-Merge-Cache: miss|hit|stale` on the response says whether it was computed or
reused, and the `meta` block reports per-source status and merge counters.

## Hardware verification status (2026-09-25)

Device: ESP32-S3 rev v0.2, 8 MB PSRAM, MAC `44:bd:8d:61:b9:e8`, on
`/dev/cu.wchusbserial10`. It is an Elecrow CrowPanel, confirmed by the
touch-capacitive `bm8563_min` driver. Build, flash and boot were all verified.

**The board boots and parses NVS correctly.** Full boot log confirms
`Loaded radar settings: lat=39.4000, lon=-104.5800, range=50.00 km, poll=25.0 s`.
Poll defaulted to 25 s because the device's NVS predates the new `poll` key, which
is exactly the upgrade path `LoadRadarSettings` was written to handle. Credentials
and radar settings both restore, WiFi STA associates, and the app partition fits
with 73% free.

**End-to-end data fetch is blocked by network topology, not by code.** Two
independent problems, both outside the firmware:

1. The device has no internet route. Both
   `auth.opensky-network.org` (token) and `opensky-network.org` (states) fail
   with `ESP_ERR_HTTP_CONNECT` after the full 15 s connect timeout. So the
   direct-OpenSky path cannot work from this board on this network.
2. The device cannot reach the dev machine. It sits at `192.168.212.36` on
   WiFi "Vicious", while the Mac is on wired `en0` at `192.168.213.57`. The two
   are on separate segments and traffic is not routed between them: the device
   can reach its own web server, but a raw `nc -l` listener on the Mac received
   nothing from it, and the device could not TCP-connect to the merge service.
   macOS firewall was checked and is disabled, so this is AP/VLAN isolation.

The firmware path itself is confirmed working up to the socket: the device
builds the request correctly, including appending the bounding box to a
configured data URL that already has no query string:

```
OpenSky: Request URL: http://192.168.213.57:8000/states/all?lamin=38.949551&lamax=39.850452&lomin=-105.162933&lomax=-103.997070
```

`POST /setdata` was exercised against the real board and returned
`Data source saved` / HTTP 200, so the webserver-to-NVS-to-memory path works.

**To finish the end-to-end test, the merge service must be reachable from
`192.168.212.0/24`.** Any of these work: run the service on a host on that
subnet, put the Mac on the "Vicious" WiFi instead of the wired adapter, or add
a port forward on the router.

## Open issues

- The radar's config web server has no authentication; anyone on the Wi-Fi can
  replace the OpenSky credentials or the data source URL.
- `src/components/lvgl__lvgl` (including demos and assets) is committed in full.
- OpenSky API credits are a per-day budget. The radar's default 25 s poll is
  about 3,450 requests/day, which exceeds the 400/day anonymous quota, so
  anonymous operation needs a longer poll interval or server-side credentials.
- `SHOW_AIRCRAFT_LABELS` in `radar.c` and the port-overlap in `main.c` are
  pre-existing and untouched.
